# 桌内「轻松聊天」体验改造计划

状态：implemented and verified（2026-09-11）
范围：用户进入具体桌后，直到收桌；不修改匹配、登录、好友、知乎 OAuth 与 3D 场景资产。

验收证据：连续消息流、回放恢复、输入法安全发送、按需阶段小结、证据回跳、单一覆盖层与收桌确认均已实现；前端 check/build/契约验证通过，后端 532 项回归通过。真实联调以 3 位成员 + 当前用户 + 圆桌主持共 5 个角色运行，模型超时时阶段小结自动使用证据约束的本地结果，不向用户暴露技术失败。

## 1. 目标

桌内只保留一件主任务：聊天。

阶段总结、主持介入、历史、证据与收桌均为辅助能力：默认安静，需要时出现，用完即退场。除项目名和完成任务所必需的文字外，删除全部解释性文本、状态口号、重复标签和装饰性短文案。

## 2. 同类产品结论

- 飞书智能会议纪要：会中实时总结，会后提供会议总结、章节与待办；结论可回到原文。可借鉴「阶段产物 + 原文溯源」，不照搬会议文档界面。
- Google Meet「Take notes for me」：用 `Summary so far` 帮助迟到用户跟上；决策区分 `Aligned / Needs Further Discussions / Disagreed / Shelved`。可借鉴明确区分共识、待议和分歧。
- Slack AI：总结是对当前会话的按需动作，完成后通知；来源藏在 `More details`，不长期占据聊天界面。可借鉴渐进披露。
- Notion AI Meeting Notes：摘要引用可悬停预览并跳到原文；用户可以继续编辑或重试摘要。可借鉴可追溯和可直接修改。
- Granola：AI 增强用户自己的笔记，支持查看每条结论的原话，并用自然语言要求重写。可借鉴「用户拥有总结」而非四个抽象反馈标签。
- Teams Intelligent Recap：会议中专注交流，结束后将回顾、记录、文件和任务集中到独立 Recap。可借鉴实时界面与沉淀界面分层。

## 3. 当前问题

### 结构问题

- 主题卡、状态条、桌边反馈、座位提示、聊天框、总结卡、收桌按钮同时争夺注意力。
- 同一个动作存在多个入口；同一个状态被多处重复表达。
- `App.tsx` 同时持有场景、入席、通知、历史、总结、收桌等大量 UI 状态，导致界面层之间缺少唯一仲裁。

### 功能问题

- 总结是常驻大卡片，反而压住聊天。
- 默认 fallback 总结为空，却仍展示完整容器和反馈按钮。
- 纠偏使用四个抽象标签；三种纠偏缺少输入，当前会触发服务端错误。
- 总结 revision、证据与聊天没有形成顺畅的可追溯体验。

### 视觉问题

- 玻璃卡、胶囊按钮、描边、高亮、英文 kicker 和多重浮层混用，形成演示玩具感。
- 3D 场景、粉色聊天层和黑色总结层分别属于不同视觉语言。
- 弱文本过多，真正的发言和当前问题反而不突出。

## 4. 目标交互

### 桌内默认态

只显示：

1. `组一桌`；
2. 当前问题；
3. 发言流；
4. 输入框；
5. 一个更多菜单。

主持发言与成员发言进入同一消息流。环境音、设置、历史、总结、收桌放入更多菜单；存在安全或失败问题时才出现短暂提示。

### 阶段总结

- 默认不常驻。
- 手动触发入口为更多菜单中的「总结」；阶段边界触发时，主持人在消息流插入一条可展开的「阶段小结」。
- 折叠态最多三行：`已经确认`、`仍待讨论`、`接下来`。
- 展开后显示完整内容；证据仅在点击某一条时出现并跳到原消息。
- 没有有效内容时不发布空总结，显示一次短提示后回到聊天。

### 纠偏

- 删除四个常驻反馈胶囊。
- 总结展开态仅保留「修改」入口。
- 点击后出现单行输入：用户直接说遗漏或错误；提交后生成新 revision。
- 用户继续发言即视为继续推进，不需要「可以继续推进」按钮。

### 收桌

- 收桌放入更多菜单。
- 第一次点击打开简短确认；完成后进入独立收桌卡，不与实时聊天层叠加。

## 5. React 层改造

### 组件边界

```text
TableRoom
├─ RoomHeader           项目名、当前问题、更多菜单
├─ ConversationSurface 消息流、主持消息、阶段小结消息
├─ Composer             发言输入
├─ SummarySheet         展开总结、修改、证据定位
├─ HistorySheet         历史消息
└─ TransientNotice      唯一短暂状态提示
```

### 状态规则

- 使用一个 `useReducer` 管理互斥 UI 层：`none | join | summary | history | close_confirm | closing_card`。
- 任意时刻最多一个 sheet/dialog；新层打开时关闭旧层。
- 网络状态留在 live store；纯展示状态留在 room reducer，禁止同一状态双份保存。
- 通知只有一个槽位，成功提示自动消失；错误提示必须给出恢复动作。
- `StageSummaryPanel` 改为 `SummaryMessage + SummarySheet`，不再是固定悬浮面板。
- 将 `ValleyExperience` 拆成容器和视图组件；容器负责副作用，视图只接收显式 props。

## 6. 视觉规则

- 3D 是环境，聊天是主体；进入桌内后背景降低对比度和饱和度，不与文字竞争。
- 同屏最多一个实底内容面板；禁止多个玻璃卡叠加。
- 只保留一套圆角、一套描边、一种主按钮样式。
- 中文为主；删除 `STAGE CHECKPOINT`、`Table Host`、`PASS`、`SILENCE` 等内部词。
- 除项目名外不使用装饰性大标题；正文不使用全大写英文。
- 状态变化优先通过位置和内容表达，不再为每个状态增加标签、圆点和说明。

## 7. 文案清扫规则

每段可见文字必须至少满足一项：

1. 是用户或主持人的真实内容；
2. 帮助用户完成当前动作；
3. 解释错误并提供恢复方式；
4. 是法律、安全或授权所必需。

否则删除。

优先删除：

- 品牌口号和场景说明；
- `瑞士山谷 · 正在发生`、`探索进行中` 等装饰状态；
- `桌边反馈`、`第五席 · 已入席` 等重复标签；
- `你的真实经历，已经来到桌边`、`这句话已经递到桌面上` 等成功解释；
- 入席大段教育文本；
- summary 的英文 kicker、覆盖句数、内部 Agent 名称；
- 同时出现的按钮文字、状态文字和 toast 中的重复信息。

保留：项目名、当前问题、成员名、发言、必要按钮、错误恢复、总结正文和按需证据。

## 8. 实施顺序与达标标准

### P0 功能止血

- 修复纠偏 500、错误成功态、空总结和 revision 历史。
- Host 慢调用不阻塞真人状态广播。

达标：四类后端合同测试通过；真实页面不存在失败后显示「已收到」；空总结不发布。

### P1 信息架构收敛

- 落地单一 Room UI reducer。
- summary、history、join、close 改为互斥层。
- 主持消息和阶段小结进入消息流。

达标：默认桌内视口只保留项目名、问题、消息、输入框和更多菜单；任意时刻最多一个浮层。

### P2 React 拆分

- 拆分 `ValleyExperience`；分离副作用与纯视图。
- 删除重复状态和重复入口。
- 为 reducer、summary revision、错误恢复补测试。

达标：桌内页面组件职责单一；关键流程不依赖多个布尔值组合；现有实时合同不回归。

### P3 视觉与文案减法

- 建立统一 token；移除英语 kicker、状态胶囊和多层玻璃卡。
- 按第 7 节逐字清扫桌内全部可见文本。

达标：同屏一个实底面板；无内部 Agent 名、实现状态或解释性成功文案；360px 和桌面宽度均以聊天为视觉中心。

### P4 验收

- 两名参与者与一名观察者完成：入席、连续发言、主持介入、阶段总结、修改总结、证据跳转、收桌。
- 做键盘、窄屏、reduced-motion、断网与慢 provider 验收。

达标：五分钟体验中，用户无需理解 Agent 架构；从入席到第一次发言不超过一个决定；总结不遮挡输入和最新消息；所有成功状态无需额外解释即可理解。

## 9. 非目标

- 不增加 dashboard、Agent 状态面板、模型选择、分析过程或更多常驻按钮。
- 不为展示技术能力暴露多 Agent 角色。
- 不重新设计匹配、个人中心、好友、知乎授权或 3D 资产。
